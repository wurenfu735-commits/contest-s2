# 09 · 问题总结：按键完全无响应（P1 v2 上板验证）

> 一次典型的"软硬件都对、但就是不工作"的排查全过程。记录价值：①团队复用排查思路 ②答辩时讲"如何定位隐蔽 bug"的素材 ③避免同类错误再犯。

## 一、现象描述

| 项 | 内容 |
|---|---|
| 现象 | 烧写 P1 v2 bit 后，**屏幕上八彩条正常显示**，但按板载 KEY1/KEY2 **完全无反应**（画面不切换任何图案） |
| 迷惑点 | 显示链路一切正常（彩条、状态带、PLL 锁定指示都对），**只有按键功能失效** |
| 误判方向 | 第一反应是"按键引脚约束错了"或"按键坏了"——**两个方向最终都被证明是错的** |

## 二、排查过程（七步，逐步排除）

| 步 | 动作 | 结论 |
|---|---|---|
| ① | **单独仿真消抖模块**（`tb_debounce.v`） | 静置无脉冲、按下出 1 个脉冲、抖动被滤除 → **ALL PASSED**，逻辑"看起来没问题" |
| ② | **查编译日志 + 资源报告** | `run.log` 显示 `I_button[0] LOCATION = D5`，`phy.area` 确认 D5/A9 已进 bit → **约束生效** |
| ③ | **查开发板手册** | 手册原文："板载 4 个金属弹片按键 KEY1~KEY4，按下为低电平"，引脚 KEY1=D5/KEY2=A9 → **与我们的约束、极性假设完全一致** |
| ④ | **烧官方现成例程**（`2_key_led\key_led.bit`） | 按 4 键流水灯效果与文档一致 → **按键硬件、引脚、极性全部正常** |
| ⑤ | **查手册板卡布局图** | 发现按键在**板子下边缘偏左**，而用户按的是**板子左边缘**（GPIO 扩展口排针区，没有按键）→ **纠正了操作位置** |
| ⑥ | **改对位置后仍无反应** → 回到源码逐行读 | **发现 `debounce_btn.v` 的计数器位宽不足**（见下） |
| ⑦ | 修复 + **真实参数仿真** + 重新综合上板 | **完全实现功能** ✅ |

## 三、根本原因（技术细节）

```verilog
localparam SAMPLE_MAX = CLK_FREQ / 1000;   // 74_250_000 / 1000 = 74250
reg [15:0] sample_div;                     // ❌ 16 位最大 65535
...
end else if (sample_div == SAMPLE_MAX - 1) // 需要计到 74249 —— 永远到不了！
```

- 采样分频计数器是 **16 位**（上限 65535），但需要计到 **74249**（= 74.25MHz ÷ 1000 − 1）
- 计数器在 65535 处回绕，**`sample_tick` 永远不会产生** → 消抖状态机从不采样 → **按键事件永不生成** → 按什么都没用
- 而 VTC、测试图、HDMI 输出完全不依赖这个计数器 → **画面一切正常**，极具迷惑性

### 一个"反向铁证"：综合器早就看穿了

| 版本 | 寄存器 reg | LUT6 | 说明 |
|---|---|---|---|
| 修复前（22:01） | 1256 | 761 | 综合器**证明"这段逻辑永远不触发"，把整个消抖链条优化掉了** |
| 修复后（22:19） | **1409** | 941 | 完整消抖逻辑被保留（+153 寄存器） |

→ 换句话说：**旧 bit 里消抖模块 фактически 不存在**。资源数据本身就证明了 bug 的存在。

## 四、为什么这个 bug 这么难发现（三层掩盖）

| 掩盖层 | 具体表现 | 教训 |
|---|---|---|
| **① 测试参数与实际不符** | TB 为了跑得快用了 `CLK_FREQ=1000`（SAMPLE_MAX=1，不发生溢出）→ 仿真 ALL PASSED，**恰好掩盖了位宽问题** | **测试必须至少有一遍用真实参数**（已补 `tb_debounce_real.v`） |
| **② 综合器静默优化** | 死逻辑被优化掉，波形/资源报告都不会报错 | 关注**资源数据异常**（如某模块"该占资源却没占"） |
| **③ 现象误导排查方向** | "画面正常、按键无效"让人先怀疑引脚/硬件，而不是消抖参数 | 排查要**从信号链上游往下**：按键→消抖→状态机→图案选择→输出 |

## 五、修复内容

| 文件 | 改动 |
|---|---|
| `rtl\debounce_btn.v` | 计数器位宽 **16 → 24 位**（24 位可计到 1677 万，覆盖 50M/74.25M/148.5M 全部时钟），并在注释里写明原因 |
| `tb\unit\tb_debounce_real.v` | **新增**：用真实 74.25MHz 参数验证（专门抓"只在真实参数下暴露"的 bug） |
| `tb\unit\tb_debounce.v` | 保留（快速逻辑 + 抖动过滤验证） |

**验证结果**：
```
[1] 快速逻辑用例（1kHz）     → ALL PASSED
[2] 真实参数用例（74.25MHz） → REAL-PARAM ALL PASSED
    idle 30ms→0脉冲 / 按下30ms→1脉冲 / 松开→仍1个 / 再按→2个
```

## 六、可复用的检查清单（写 RTL 时对照）

1. **位宽检查**：计数器的最大值是否装得下目标值？（`SAMPLE_MAX-1` vs `2^W-1`）
   - 74.25MHz 下 1ms 分频 = 74250 → 至少 17 位；本项目统一用 24 位留余量
2. **参数化后必须用真实参数跑一遍仿真**（小参数会掩盖位宽/时序问题）
3. **关注资源异常**：如果某模块"几乎不占资源"，先怀疑它是否被综合器优化掉了
4. **排查顺序**：输入引脚 → 消抖 → 事件生成 → 状态机 → 输出（逐级用 LED/探针打点）
5. **硬件验证兜底**：怀疑硬件时，烧官方现成 bit 做对照实验（最快排除法）

## 七、答辩价值（可直接讲的故事）

> "我们的按键功能上板后完全无响应。我们用了七步排查：先单独仿真消抖模块通过，再核对编译日志确认引脚约束生效，然后查手册、烧官方例程排除硬件问题，最后回到源码逐行检查，发现采样计数器位宽装不下分频值，导致采样脉冲永不产生。修复后重新综合，寄存器数从 1256 增加到 1409——**综合器早就算出那段逻辑永远不会执行并把它优化掉了**。这个问题让我们建立了'测试必须用真实参数'的规范。"

**这段故事体现的能力**：分层排查、对照实验、源码级定位、用资源数据反证——比"功能做出来了"更能体现工程素养。
