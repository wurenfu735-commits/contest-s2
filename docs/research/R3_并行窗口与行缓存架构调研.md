# R3 · 并行窗口与行缓存架构调研（2026-10-17 补做）

> 起因：用户指出补调研（"被官方框死的一定遵守，可自主掌握的范围一定深度调研"）。
> 主题：box filter 增量求和 / 环形行缓存 / 多像素并行窗口 / 自适应阈值组织方式。
> 方法：GitHub REST API（本机 raw/gh 直连不可用，走 api.github.com），深挖 2 个仓库完整 RTL。
> 结论：**现有 v2 架构与主流做法方向一致；三个可选优化经权衡均不采纳（见第四节）。**

## 一、深挖对象与核心发现

### 1. dannyboy1024/fpgaconv2d —— 3×3 对称卷积（line-buffer + running sum）
- **增量滑窗（running sum）**：每行部分和链式更新 `dep[row][1] <= rd_upper + products_buf[row][2]`——新列滑入加、旧列滑出减，**每像素 O(1)**，不整窗重算。
- **部分和存块 RAM**：把"行内部分和"（而非灰度）存进 mem[512]，下一行复用，省掉重复加法树。
- 对称系数折叠：共享乘法再拼接。

### 2. AngeloJacobo/sobel_convolution —— 实时 Sobel（separable 分解 + 部分和缓存）
- **可分离分解**：2D Sobel 拆两趟 1D——横向 `temp1+temp2+temp3`（Y 核行和）/ `-temp3+temp1`（X 核行差）→ 部分和存 **6 块 RAM**（X/Y 各 3 行）→ 纵向再组合。
- 全程无乘法器，1 像素/拍。

## 二、与我们的 v2 对照

| 维度 | dannyboy1024 | AngeloJacobo | **我们 v2** |
|---|---|---|---|
| 并行度 | 1 像素/拍 | 1 像素/拍 | **4 像素/拍（全 1280）** |
| 求和方式 | running sum 增量 | separable 两趟 + 部分和 RAM | separable 第一步（col3 横向和）但**每像素重复求和** |
| 行缓存 | 单块存部分和 | 6 块存部分和 | 4 块下沉链存灰度 + 1 块判决 |
| 可借鉴点 | 增量滑窗 | 部分和缓存、分离思路 | — |

**结论**：我们的 v2 与主流 separable 方向一致；差异在于"每像素重算 col3"——加法器冗余但结构最直白。

## 三、环形行缓存（ring line buffer）评估

**原理**：N 块行缓存 + 写指针轮转 + 读指针"模减 N-1"取最老一行，**免逐级下沉搬运**。

**针对我们的痛点**：v2 的 line2/line3 逐级下沉链（`S_line1_doa → line2 → line3`）是 v1/v2 两个"地址错位" bug（坑 33、以及本轮 line2 写地址 wr_dn→wr_gray 的错位）的根源。环形方案天然无错位。

**为什么现在不换**：
1. v2 已验证 100% 正确、上板已出正常轮廓，换行缓存 = 控制逻辑重写 + 全量重新仿真（成本 > 1 个调试轮次）；
2. 资源不紧张（当前算法 ~1134 LUT / 全设计 50%），无替换动机。

## 四、决议（按"资源与效果优先、避免复杂化"）

| 候选优化 | 收益 | 决策 |
|---|---|---|
| A. col3 改 running sum 增量 | 省 ~200-300 LUT | ❌ 不改：LUT 与时序都宽裕，收益不抵复杂度 |
| B. 换环形行缓存 | 根除下沉链错位类坑 | ❌ 现状不改；**下次若要扩核加行（如 5×5），一律直接上环形方案**，不再加下沉链 |
| C. 部分和存 RAM 跨行复用 | 省加法树 | ❌ 不适用：我们 4 像素/拍并行取窗口，不是串行滑窗 |
| D. 自适应阈值组织方式 | 与 R1 自研方案一致 | ✅ 维持 |
