## 〇、先纠正一件事：扩展不是"5 条"，是"2 + 5"

我们 `docs/01` 和 `docs/06` 一直按 2.4 的编号（①风格化 ②目标检测 ③机电联动 ④性能优化 ⑤自主创意）当成"扩展 5 条"在做。但 **2.6 评分标准把它重新拆成了两组，而且明说分值不等权**：

| 组                | 项目                                                                                            | 官方原话                                                                                                  |
| ---------------- | --------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **一、基础扩展项（2 项）** | (1) 视频图像风格化处理或视觉增强<br />(2) 基于视频内容的目标检测与识别                                                    | 「完成 **2 项**且效果良好，可获得扩展部分**一半以上**的分值」                                                                  |
| **二、高阶挑战项（5 项）** | (1) 多算法切换与状态显示<br />(2) 动态目标跟踪与坐标叠加<br />(3) 处理延迟可视化<br />(4) 硬件运动目标检测<br />(5) 画面自动曝光/白平衡等优化 | 「完成**多项高阶挑战**且系统运行稳定、展示效果突出，可获得**较高分**」<br />「基础扩展项与高阶挑战项均不设置单项固定分值……**完成相同数量扩展要求的情况下，高阶挑战项可获得更高分数**」 |

**三条直接结论：**

1. **2 个基础扩展是"入场券"** —— 只做这 2 项，封顶在"扩展部分一半分"。我们现在这 2 项目前是 **0/2**，这是最大失分点。
2. **拉开差距靠 5 个高阶挑战** —— 单项没固定分值、但权重更高。我们现在 **0/5**。
3. **2.4 的第 (3) 项"结合移动平台实现外部控制"在 2.6 里没有单列成评分项。** 所以**不用为它去买电机**；`docs/01` 里"暂不做机电联动"的决定，按评分表看是对的。

> `docs/06` 把"多算法按键切换"记成"扩展⑤自主创意"、"性能优化可视化"记成"扩展④性能优化" —— 这两项在 2.6 里其实分别对应**高阶挑战(1)** 和**高阶挑战(3)**，属于**更高分**的那一组。这是好消息：本来就打算做的事，实际权重比以为的更高。

## 二、该做什么：按"每 slice 出多少效果"排序

### 2.1 硬约束：先腾资源，否则什么都加不进去

**两版位流实测对照（`phy_1/…_phy.area` + `route.qor`，2026-10-19 取数）**：

| 资源 | v5（官方 OSD） | **B5（`mixer_lite` + 2 色 Logo，★ 现行）** | 说明 |
| --- | --- | --- | --- |
| **slice** | 16,616 / 21,216（**78.32%**） | **14,547 / 21,216（68.57%）** | 按 80% 安全线：357 → **2,426** |
| lut6 | 14,534 | **12,239** | −2,295 |
| eram20k | 60 / 108（55.56%） | **60 / 108** | 余 48 块 ≈ 120 KB |
| DSP | 9 / 40（22.50%） | **8 / 40** | 富余，**乘加尽管展开** |
| slice reg | 14,071 / 42,432 | **14,054 / 42,432** | — |
| 时序 | SWNS **+0.101 ns** / HWNS +0.020 ns | **SWNS +1.311 ns** / HWNS +0.020 ns | 都是 0 违例 |

```
21,216 × 80% = 16,973 slice（TD 建议安全上限）
16,973 − 14,547（B5 实测） = 2,426 slice ← 现在能用的预算
```

> 上表的 B5 是**已经做出来并跑完 P&R 的**（`bitbank/OUR_b5_mixerlite_logo2c.bit`），不是估算。
> 下面 §2.1 的推导过程保留下来是为了留下"为什么这么做"的证据链，结论以本表为准。


**所以第 0 步（必做，否则后面全部卡死）：脱离官方 OSD 通路（= 自研 `mixer_lite`）。**

> **⚠️ 2026-10-19 重大更正**：原方案写的是"定义 `OSD_SELF_DEV` 即可回收 ≈1,960 slice"，  
> **这条现在是错的，照做会翻车**。原因：`u_hdmi_mixer` 在 `design_top_wrapper.v:875` 是**无条件例化**的，  
> `` `ifdef OSD_SELF_DEV `` 在 901 行只控制**要不要再叠一层** `osd_overlay`。  
> B4 把 `hdmi_mixer.v` 从 182 行无 Logo 版换成 909 行官方 OSD 版之后，这个开关就**从"二选一"退化成了"只能加不能换"**：  
> 定义它的结果是 **双 Logo + 资源反而涨到 ≈80.6%**。详见 `docs/17` 优化项 O1。

**正确做法（方案 A）**：写 `rtl/mixer_lite.v`（约 150 行）替代官方 `hdmi_mixer` 的非 OSD 部分 ——  
它只做三件事：`O_video_rd_en = I_video_de`、vsync/hsync/de/data 打 2 拍、串接我们的 `osd_overlay`。  
**顶层不再例化官方 `hdmi_mixer`（文件保留不删）**，属于 L3 顶层连线，不动任何官方文件内容。

**★ 已有实测（2026-10-19 跑过，不是估算）**：把官方 Logo 位图临时换成常量后完整跑 syn+phy，
**slice 16,616 → 14,291（−2,325）**、`u_hdmi_mixer` LUT **2,551 → 211**、Setup **+0.101 → +0.655 ns**、
DSP **9 → 8**。即 **一块 Logo 位图 = 全片 10.96% + 1 个 DSP + 0.55 ns 时序余量**。

| 做法 | LUT | Logo 画质 | 实测/估算 |
|---|---|---|---|
| 现行（官方 `hdmi_mixer`，25bit） | 2,551 | 579 色 | **实测** |
| Logo 完全去掉（不合规，仅作基准） | 211 | 无 | **实测** |
| **`mixer_lite` + 自研 OSD（`osd_overlay`，Logo 2 色 / 2bit）** | **623**（含 208×156 面板 + 两行文字） | **2 色 + 透明，与官方同一张图** | **已实测并出位流** |

- **实际收益（B5 实测）**：`u_hdmi_mixer` 2,551 LUT → `u_mixer_lite` **0 LUT + 78 reg**，
  OSD 总量压到 `u_osd_overlay` **623 LUT**；全片 slice **16,616 → 14,547（−2,069，−9.75 pt）**，
  Setup **+0.101 → +1.311 ns**，DSP 9 → 8，eram 不变。
- **真预算**：16,973（80% 线）− 14,547 = **2,426 slice**（现状曾只有 357）
- **为什么最后选 2 色而不是 16 色**：这张图 579 色里前 2 色（深蓝 `#1C2D4E` + 红 `#ED1C24`）占 59.3%，
  且用户明确要求「把区域主颜色定下来就行」。2 色版已经把 Logo 位图开销压到几乎为零，
  再上 16 色只是徒增 400 LUT 换肉眼看不出的差异。
  **对比图**：`src/p1_colorbar/tools/logo_palette_cmp.png`（原图 / 16 色 / 8 色 / 4 色 四联）；
  2 色版渲染验证：`src/p1_colorbar/tools/our_logo.png`（6,387 像素与官方图逐个对上）
- **合规**：不改官方文件；位图**数据**沿用官方 `anlogic_logo_rom.v` 同一份素材，只做颜色量化。
  口径：「Logo 位图沿用官方素材，按 16 色调色板重新编码以缓解 LUT 压力，平均误差 0.56%」
- **⚠️ Logo 不能删**：官方 2.3(4) 硬性要求"包含安路标识 Logo"。我们做的是**换编码方式，不是删 Logo**。
- **连带价值**：官方 mixer 的 OSD 文字写死在 909 行里（"安路 CNT:" + 固定计数器）。
  高阶(1) 的模式名、高阶(2) 的坐标、高阶(3) 的延迟 ms **都要往屏上写** → `mixer_lite` 本来就必须做，
  省资源只是顺带收益。
- **代价**：需重新上板确认 OSD 时序与 Logo 显示（约半天）；切完是**新基线**，v5 时序数据不能沿用


### 2.2 一个关键杠杆：B4 的 OSD 是"免费"的基础设施

官方 `osd_char_lib.v`（ASCII 5×7 + 中文字模）+ `hdmi_mixer.v` 的动态渲染通路已经在工程里、已经在跑。这意味着：

| 高阶挑战项              | 要靠 OSD 做什么                              | 额外成本                                                |
| ------------------ | --------------------------------------- | --------------------------------------------------- |
| (1) 多算法切换与**状态显示** | 屏幕显示当前算法名（"EDGE" / "CARTOON" / "TRACK"） | **几乎为零**，字符库现成                                      |
| (2) 目标跟踪与**坐标叠加**  | 屏幕显示目标坐标 `X:640 Y:360`                  | **几乎为零**，`hdmi_mixer.v` 已有 `S_dyn_dec_digit` 数字渲染逻辑 |
| (3) **处理延迟可视化**    | 屏幕显示帧计数 / 延迟 ms                         | 只加计数器，显示部分复用上面                                      |

**这是本轮最划算的一笔：三个高阶挑战项的文字呈现部分，B4 已经替我们做完了。**

### 2.3 推荐组合（7 项全打，按依赖顺序）

```
                    ┌─ 基础扩展② 目标检测与识别（颜色分割 + 质心 + 框 + 文字）
                    │        ↓ 顺带产出
                    │   高阶挑战(2) 目标跟踪与坐标叠加
                    │
复用现有 OSD ───────┼─ 高阶挑战(1) 多算法切换 + 状态显示
      ↑             │   高阶挑战(3) 处理延迟可视化
      │             │
      └─────────────┴─ 基础扩展① 风格化（卡通化：颜色量化 + 边缘 + 3×3 膨胀）
                             ↓
                       高阶挑战(4) 帧差运动检测（独立支路，不与上面抢窗口）
```

**为什么是这条链**：目标检测和卡通化**都只需要 3×3 邻域**，可以共用同一个窗口生成器（`docs/17` 优化项 O4 的"级联流式算子"思路）；多算法切换只是后级 mux；延迟可视化和状态显示全靠现成 OSD。**整套东西共用一套行缓存，这是能把 7 项塞进 2,319 slice 的唯一办法。**

## 三、逐项实现方案

### 基础扩展② 目标检测与识别 ★最高优先（现在是 0/2 里的一项）

**官方要求**：「实现基于视频内容的目标检测与识别功能，对简单目标进行识别，并在输出画面中**叠加检测结果与文字说明**」

| 环节     | 做法                                              | 参考                                                                             |
| ------ | ----------------------------------------------- | ------------------------------------------------------------------------------ |
| 颜色分割   | RGB→YCbCr，用 Cb/Cr 阈值判色（红球/肤色）。定点实现，避免除法         | `delhatch/Red_Tracker`、`Xu-Zihao-cqu/fpga-vision-gesture-controller`（肤色分割定点写法） |
| 连通域/质心 | **行/列投影统计**（每行数命中像素数、每列数命中像素数），峰值即质心；比真连通域标号省得多 | `Red_Tracker` 的投影峰值法                                                           |
| 包围框    | 用投影的 min/max 行列坐标画矩形（4 个比较器 + 计数器，无存储）          | —                                                                              |
| 文字说明   | 叠加 `RED BALL` + 坐标数字，**复用官方 OSD 字符库**           | `docs/14`                                                                      |
| 防抖     | 7 帧滑动投票（避免框闪烁）                                  | `Xu-Zihao-cqu` 的投票做法                                                           |

- **预算**：约 **600 slice**（分割 300 + 投影统计 200 + 框 100）；投影统计需要 720×2 个小计数器，用 ERAM 存（约 3 块）
- **验收**：红色物体在镜头前移动，框跟随、文字显示坐标、7 帧内不抖

### 基础扩展① 风格化处理（卡通化 + 伪彩色）★第二优先

**官方要求**：「实现视频图像**风格化处理或视觉增强**功能，如边缘提取与区域填充等」

- **做法**：边缘支路（复用现有边缘检测输出）→ **形态学膨胀 3×3**（把断线连起来）；颜色支路 → **颜色量化**（每通道保留高 3~4 位，即 `{r[7:5],3'b000}`）→ 两路按位 AND 融合
- **借**：`LynnnPush/cartoonize_rcd` 的融合范式（灰度→中值→自适应阈值 ∥ 双边 → AND）；`redpower1998/fpga_image` 的 `erosion/dilation` 写法
- **注意**：双边滤波太贵（参考实现 4.6k LUT），**不做双边，改颜色量化**，视觉差异小但省 4k LUT

**★ 2026-10-19 重要修正：预算从 450 下调到 ≈200**

`rtl/edge_adaptive_96.v` 里**已经有 6 条级联行缓存**（`blk_mem_gen_zhenghe` × 6，各 32 bit = 4 像素 × 8 bit 灰度），  
加上当前行就是 **7 行 × 4 像素的灰度窗口**。所以灰度域的 3×3 膨胀/腐蚀**不需要任何新行缓存**，  
只要把窗口引出来加一个组合比较树：

| 子项        | 原估算     | 修正后      | 依据                      |
| --------- | ------- | -------- | ----------------------- |
| 3×3 膨胀    | ~150    | **≈60**  | 窗口已存在，只加 9 输入取大树        |
| 颜色量化      | ~200    | ~100     | 只截高位 + 与边缘 AND          |
| 融合/模式 mux | ~100    | ~40      | 已有 `I_mode` 四态 mux，扩位即可 |
| **合计**    | **450** | **≈200** |                         |

- **⚠️ 实现陷阱**：我们走 **4 像素/拍**，3×3 窗口的"左邻列"会跨拍  
  （每拍第 1 个像素的左邻 = 上一拍第 4 个像素）→ **必须加一个 8bit 跨拍像素拼接寄存器**。  
  忘了它窗口会整体错位 1 像素，卡通化出竖条纹。这条已写进 `research/R2` 自检清单。
- **加送一个几乎免费的模式：伪彩色**（`research/R4`）：8bit 灰度 → 蓝→青→绿→黄→红五段线性渐变，  
  纯组合逻辑 `x*5 = (x<<2)+x`，**≈35 slice、0 ERAM、0 行缓存**。  
  它本身就是官方说的"视觉增强"，和高阶(1) 的模式切换天然契合。

### 高阶挑战(1) 多算法切换与状态显示 ★性价比最高

**官方要求**：「通过按键实现多种图像处理算法的**实时切换**，并在画面中显示当前算法状态，**力求切换平稳**」

- `I_mode` 端口已经存在（四态机：0 原图 / 1 官方判决 / 2 我们的判决 / 3 分屏），只需**扩成 3bit 支持 6~8 种模式**
- 按键：`rtl/debounce_btn.v` 已有，但**板载 KEY 接不到**（在扩展口 N2/J14）→ 要么飞线，要么改用扩展口按键，**这个是硬件动作，要提前做**
- "切换平稳"：切换发生在**帧边界**（用 `vsync` 对齐），避免撕半帧——这是官方"力求切换平稳"的考点，必须做
- 状态显示：OSD 现成
- **预算**：约 **200 slice**

### 高阶挑战(3) 处理延迟可视化 ★便宜

**官方要求**：「设计延迟测量方案，将**采集到显示的延迟**进行可视化（如帧计数）」

- 做法：采集端打进一个随时间自增的标记（或帧号），显示端减出来 → 延迟帧数；配合已知帧周期换算成 ms
- 显示：OSD 数字（`hdmi_mixer.v` 已有 `S_dyn_dec_digit` 渲染通路）
- **预算**：约 **150 slice**
- **副作用（正面）**：这个数直接就是报告里"端到端延迟"的实测值，`docs/13` 第 201 行要求"必须出现的数字"之一

### 高阶挑战(4) 帧差运动检测 ★中等

**官方要求**：「用硬件逻辑实现**帧差法**等运动检测，并叠加**运动区域提示或计数**」

- 做法：存**降采样的前一帧**（如 160×90 灰度 = 115 Kbit ≈ **6 块 ERAM**），当前帧降采样后逐块相减、阈值、统计运动块数
- **关键取舍**：不要存全分辨率帧差（要 1.2 Mbit），降采样到 160×90 足够做"运动区域提示"
- **预算**：约 **300 slice + 6 ERAM**（ERAM 剩 45 块，够）

### 高阶挑战(2) 目标跟踪与坐标叠加 ★增量最小

**官方要求**：「对画面中特定**颜色或形状目标**的动态跟踪，叠加**跟踪标识或坐标信息**」

- 在"基础扩展②"的质心基础上加：帧间位移 → 方向/速度判决（状态机）→ 准星/轨迹线
- 坐标文字已由 ② 提供，这里只加方向判决
- **预算**：约 **150 slice**
- **参考**：`x-hao-v/fpga-video-gesture-control` 的"检测→决策→画面响应"闭环

### 高阶挑战(5) 图像质量自动调节 —— **改做直方图均衡，不做 AE/AWB**

> **2026-10-19 更正**：本项原判"不做"，理由是要抢 I2C 跟官方 `awb` 打架。但官方原文（PDF p16，2.5 第 5 条）写的是：  
> 「图像质量自动调节：可探索自动曝光、白平衡**或直方图均衡**等 ISP 处理，提升画面适应能力。」  
> **"直方图均衡"是官方明列的等价选项**，它纯属像素域运算，不碰 I2C、不碰 `uics520_cfg`、不碰 `awb.v`，  
> 所以本项从"放弃"改为"**可做，成本中等**"。

| 环节  | 做法                                                    | 成本                           |
| --- | ----------------------------------------------------- | ---------------------------- |
| 统计  | 每帧统计灰度 min / max（限幅到 [8,248]，避免单个噪点拉爆动态范围）            | 2 个比较器，**几乎为 0**             |
| 求倒数 | **帧消隐期**用官方 `divider` IP 算一次 `K = (255<<16)/range`    | 一帧 1 次，**不在像素关键路径上**         |
| 映射  | 像素级 `y' = (y - min) * K >> 16`                        | 1 个乘法 → **走 DSP**（我们只用 9/40） |
| 平滑  | min/max 做一阶 IIR（`min_s <= (3*min_s + min)>>2`），避免逐帧闪烁 | ~10 slice                    |
| 显示  | 作为高阶(1) 的一个模式 `STRETCH`，状态上屏                          | 复用 OSD，≈0                    |

- **预算**：约 **60 slice + 1 DSP**（原估 320，因为原方案想的是完整 256bin 直方图）
- **★ 关键教训（来自 `research/R4` 的第三方实现）**：有一种写法是  
  `wire [7:0] y = (y-min)*255/(max-min);` —— **逐像素组合除法，时序必然崩**。  
  必须把除法提到帧级，**一帧只算一次倒数，像素级只做乘法**。我们已经引入官方 `divider` IP，正好用它。

**stretch goal：真直方图均衡（CDF 映射）**

- 256 bin 统计（1 个 `eram20k`）+ 帧消隐期串行累加 256 步得 CDF + 查表
- 额外 **≈200 slice + 1 ERAM**
- **只在拉伸版跑通、且资源 < 79% 时才做**
- **⚠️ 反作用**：直方图拉伸/均衡都会**放大暗区噪声**，正好踩我们的残雪痛点。所以：
  - 只作为**可选模式**（默认关闭），现场演示只在**光线充足**时开启
  - 反过来这也是个答辩亮点：可以直接讲"我们实测 HE 会放大暗区噪声，所以默认走分段阈值而不是 HE"，说明我们理解自己的场景

### （原方案，已降级为"不做"）AE/AWB 主动控制

- 官方 `awb.v` 已有 AE/AG 通路，但**策略是官方的、文件不能改**（`docs/17` L1）
- 自己另做一套要抢 I2C 控制权、跟官方 `uics520_cfg` 打架，**风险高、收益低** → 放弃
- 低成本替代（可选，~100 slice）：把现有 awb 的增益值读出来**上屏显示**，作为"图像质量"的观察证据。评委问起来能讲，但**不宣称实现了自动调节**。

## 七、一句话总结

**基础功能 4/4 已完成，但"系统稳定性（光线剧烈变化）"缺实测证据 —— 这是唯一不用改代码、只要补测试就能拿的分，今天就要补。**
**扩展按官方 2.6 的真实结构是"2 个基础扩展 + 5 个高阶挑战"，不是"5 条"：2 个基础扩展是拿一半分的入场券（现在 0/2），5 个高阶挑战才是拉分点（现在 0/5）。**
**打法：先脱离官方 OSD 通路（`mixer_lite` + Logo 降到 16 色调色板，**Logo 保留不删**）回收 ≈1,995 slice（真预算 ≈2,350），再用"一套窗口生成器 + 后级 mux + 复用现成 OSD 字符库"把 7 项塞进去，全做 76.7%，超 79% 就按砍单顺序倒着砍。**
**两个省钱杠杆（`research/R4` 结论）：灰度域 3×3 算子复用 `edge_adaptive_96` 已有的 6 条行缓存（不新增 ERAM）；直方图的除法提到帧级（一帧一次，不在像素路径上）。**
**⚠️ 特别提醒：不要去"定义 `OSD_SELF_DEV`"，那个开关现在是坏的（会导致双 Logo 且资源反而涨到 80.6%），见 `docs/17` O1 的更正方框。**
**顺序：先搭"舞台"（高阶(1) 多算法切换，200 slice），再上"节目"（2 个基础扩展），最后加高阶(2)(3)(4)(5)。**
