## 〇、先纠正一件事：扩展不是"5 条"，是"2 + 5"

我们 `docs/01` 和 `docs/06` 一直按 2.4 的编号（①风格化 ②目标检测 ③机电联动 ④性能优化 ⑤自主创意）当成"扩展 5 条"在做。但 **2.6 评分标准把它重新拆成了两组，而且明说分值不等权**：

| 组 | 项目 | 官方原话 |
|---|---|---|
| **一、基础扩展项（2 项）** | (1) 视频图像风格化处理或视觉增强<br>(2) 基于视频内容的目标检测与识别 | 「完成 **2 项**且效果良好，可获得扩展部分**一半以上**的分值」 |
| **二、高阶挑战项（5 项）** | (1) 多算法切换与状态显示<br>(2) 动态目标跟踪与坐标叠加<br>(3) 处理延迟可视化<br>(4) 硬件运动目标检测<br>(5) 画面自动曝光/白平衡等优化 | 「完成**多项高阶挑战**且系统运行稳定、展示效果突出，可获得**较高分**」<br>「基础扩展项与高阶挑战项均不设置单项固定分值……**完成相同数量扩展要求的情况下，高阶挑战项可获得更高分数**」 |

**三条直接结论：**

1. **2 个基础扩展是"入场券"** —— 只做这 2 项，封顶在"扩展部分一半分"。我们现在这 2 项目前是 **0/2**，这是最大失分点。
2. **拉开差距靠 5 个高阶挑战** —— 单项没固定分值、但权重更高。我们现在 **0/5**。
3. **2.4 的第 (3) 项"结合移动平台实现外部控制"在 2.6 里没有单列成评分项。** 所以**不用为它去买电机**；`docs/01` 里"暂不做机电联动"的决定，按评分表看是对的。

> `docs/06` 把"多算法按键切换"记成"扩展⑤自主创意"、"性能优化可视化"记成"扩展④性能优化" —— 这两项在 2.6 里其实分别对应**高阶挑战(1)** 和**高阶挑战(3)**，属于**更高分**的那一组。这是好消息：本来就打算做的事，实际权重比以为的更高。

## 一、基础部分到底做完没有：4/4，但有一条没"测过"

### 1.1 功能项（2.3 的 4 条）

| # | 官方原文 | 状态 | 证据 |
|---|---|---|---|
| (1) | MIPI 摄像头采集 + HDMI 实时输出 | ✅ | P0 起全通路跑通，720p60 稳定 |
| (2) | FPGA 端至少一种图像处理算法 | ✅ | `edge_adaptive_96` **v5**：5×5 均值去噪 + 分段 FLOOR + 因果迟滞；仿真逐像素 0 误差，暗区 Δ=10 检出 95.9%（`docs/19`） |
| (3) | 处理后视频稳定输出、画面连续无明显异常 | ⚠️ | 实时、时序 0 违规；但**残留雪花未根治** |
| (4) | 叠加 OSD 且**包含"安路"Logo** | ✅ | 2026-10-17 深夜上板验证通过（`docs/14` / `docs/15`） |

### 1.2 评分项（2.6 的 4 条，注意和 2.3 不是一一对应）

2.6 把"**系统稳定性**"单独列成第 4 条，而且给了三个明确判据：

> 「系统长期运行**无花屏、无缓存溢出**，**光线剧烈变化时工作正常**」

| 判据 | 我们有没有测过 |
|---|---|
| 长期运行无花屏 / 无缓存溢出 | ⚠️ 只做过短时观察，**没有 30 分钟以上的连续运行记录** |
| 光线剧烈变化时工作正常 | ❌ **完全没测**。而且这条恰好踩在我们的痛点上——v4 的分段阈值就是为亮度变化设计的，但**暗光下雪花最明显**（`memory/PROGRESS.md`：暗区假边缘 0%、低对比弱边缘 85.7%） |

**所以准确说法是：基础功能 4/4 做完了，但"系统稳定性"这一条缺实测证据，且是唯一可能被判扣分的地方。**

- 这项**不用改代码**，只要补测试：`30 分钟连续运行录像` + `开灯/关灯/手电照镜头 交替 10 次` + `拔插摄像头重启`。
- 如果关灯时满屏雪花被评委判成"异常"，那就必须回头处理残雪（候选方案见 `PROGRESS.md` 暂停时的清单）。

## 二、该做什么：按"每 slice 出多少效果"排序

### 2.1 硬约束：先腾资源，否则什么都加不进去

当前官方 OSD 版 78.76%、Setup **+0.005 ns**。按 TD 官方建议 80% 上限，可用余量只有：

```
21,216 × 80% = 16,973 slice（安全上限）
16,973 − 14,654（自研 OSD 版） = 2,319 slice ← 这才是真正的预算
```

**第 0 步（必做，否则后面全部卡死）：切 `OSD_SELF_DEV`。**
- 78.76% → 69.07%，Setup 从 +0.005 ns 回到 +0.787 ns
- 不改任何官方文件，只加一个 `define`（合规性见 `docs/17` 第一节 L2）
- **代价**：Logo 从 25bit/像素变 2bit/像素（品牌双色）

### 2.2 一个关键杠杆：B4 的 OSD 是"免费"的基础设施

官方 `osd_char_lib.v`（ASCII 5×7 + 中文字模）+ `hdmi_mixer.v` 的动态渲染通路已经在工程里、已经在跑。这意味着：

| 高阶挑战项 | 要靠 OSD 做什么 | 额外成本 |
|---|---|---|
| (1) 多算法切换与**状态显示** | 屏幕显示当前算法名（"EDGE" / "CARTOON" / "TRACK"） | **几乎为零**，字符库现成 |
| (2) 目标跟踪与**坐标叠加** | 屏幕显示目标坐标 `X:640 Y:360` | **几乎为零**，`hdmi_mixer.v` 已有 `S_dyn_dec_digit` 数字渲染逻辑 |
| (3) **处理延迟可视化** | 屏幕显示帧计数 / 延迟 ms | 只加计数器，显示部分复用上面 |

**这是本轮最划算的一笔：三个高阶挑战项的文字呈现部分，B4 已经替我们做完了。**

### 2.3 推荐组合（7 项全打，按依赖顺序）

```
                    ┌─ 基础扩展② 目标检测与识别（颜色分割 + 质心 + 框 + 文字）
                    │        ↓ 顺带产出
                    │   高阶挑战(2) 目标跟踪与坐标叠加
                    │
复用现有 OSD ───────┼─ 高阶挑战(1) 多算法切换 + 状态显示
      ↑             │   高阶挑战(3) 处理延迟可视化
      │             │
      └─────────────┴─ 基础扩展① 风格化（卡通化：颜色量化 + 边缘 + 3×3 膨胀）
                             ↓
                       高阶挑战(4) 帧差运动检测（独立支路，不与上面抢窗口）
```

**为什么是这条链**：目标检测和卡通化**都只需要 3×3 邻域**，可以共用同一个窗口生成器（`docs/17` 优化项 O4 的"级联流式算子"思路）；多算法切换只是后级 mux；延迟可视化和状态显示全靠现成 OSD。**整套东西共用一套行缓存，这是能把 7 项塞进 2,319 slice 的唯一办法。**

## 三、逐项实现方案

### 基础扩展② 目标检测与识别 ★最高优先（现在是 0/2 里的一项）

**官方要求**：「实现基于视频内容的目标检测与识别功能，对简单目标进行识别，并在输出画面中**叠加检测结果与文字说明**」

| 环节 | 做法 | 参考 |
|---|---|---|
| 颜色分割 | RGB→YCbCr，用 Cb/Cr 阈值判色（红球/肤色）。定点实现，避免除法 | `delhatch/Red_Tracker`、`Xu-Zihao-cqu/fpga-vision-gesture-controller`（肤色分割定点写法） |
| 连通域/质心 | **行/列投影统计**（每行数命中像素数、每列数命中像素数），峰值即质心；比真连通域标号省得多 | `Red_Tracker` 的投影峰值法 |
| 包围框 | 用投影的 min/max 行列坐标画矩形（4 个比较器 + 计数器，无存储） | — |
| 文字说明 | 叠加 `RED BALL` + 坐标数字，**复用官方 OSD 字符库** | `docs/14` |
| 防抖 | 7 帧滑动投票（避免框闪烁） | `Xu-Zihao-cqu` 的投票做法 |

- **预算**：约 **600 slice**（分割 300 + 投影统计 200 + 框 100）；投影统计需要 720×2 个小计数器，用 ERAM 存（约 3 块）
- **验收**：红色物体在镜头前移动，框跟随、文字显示坐标、7 帧内不抖

### 基础扩展① 风格化处理（卡通化）★第二优先

**官方要求**：「实现视频图像**风格化处理或视觉增强**功能，如边缘提取与区域填充等」

- **做法**：边缘支路（复用现有边缘检测输出）→ **形态学膨胀 3×3**（把断线连起来）；颜色支路 → **颜色量化**（每通道保留高 3~4 位，即 `{r[7:5],3'b000}`）→ 两路按位 AND 融合
- **借**：`LynnnPush/cartoonize_rcd` 的融合范式（灰度→中值→自适应阈值 ∥ 双边 → AND）；`redpower1998/fpga_image` 的 `erosion/dilation` 写法
- **注意**：双边滤波太贵（参考实现 4.6k LUT），**不做双边，改颜色量化**，视觉差异小但省 4k LUT
- **预算**：约 **450 slice**（量化 ~200、膨胀 ~150、融合 ~100）

### 高阶挑战(1) 多算法切换与状态显示 ★性价比最高

**官方要求**：「通过按键实现多种图像处理算法的**实时切换**，并在画面中显示当前算法状态，**力求切换平稳**」

- `I_mode` 端口已经存在（四态机：0 原图 / 1 官方判决 / 2 我们的判决 / 3 分屏），只需**扩成 3bit 支持 6~8 种模式**
- 按键：`rtl/debounce_btn.v` 已有，但**板载 KEY 接不到**（在扩展口 N2/J14）→ 要么飞线，要么改用扩展口按键，**这个是硬件动作，要提前做**
- "切换平稳"：切换发生在**帧边界**（用 `vsync` 对齐），避免撕半帧——这是官方"力求切换平稳"的考点，必须做
- 状态显示：OSD 现成
- **预算**：约 **200 slice**

### 高阶挑战(3) 处理延迟可视化 ★便宜

**官方要求**：「设计延迟测量方案，将**采集到显示的延迟**进行可视化（如帧计数）」

- 做法：采集端打进一个随时间自增的标记（或帧号），显示端减出来 → 延迟帧数；配合已知帧周期换算成 ms
- 显示：OSD 数字（`hdmi_mixer.v` 已有 `S_dyn_dec_digit` 渲染通路）
- **预算**：约 **150 slice**
- **副作用（正面）**：这个数直接就是报告里"端到端延迟"的实测值，`docs/13` 第 201 行要求"必须出现的数字"之一

### 高阶挑战(4) 帧差运动检测 ★中等

**官方要求**：「用硬件逻辑实现**帧差法**等运动检测，并叠加**运动区域提示或计数**」

- 做法：存**降采样的前一帧**（如 160×90 灰度 = 115 Kbit ≈ **6 块 ERAM**），当前帧降采样后逐块相减、阈值、统计运动块数
- **关键取舍**：不要存全分辨率帧差（要 1.2 Mbit），降采样到 160×90 足够做"运动区域提示"
- **预算**：约 **300 slice + 6 ERAM**（ERAM 剩 45 块，够）

### 高阶挑战(2) 目标跟踪与坐标叠加 ★增量最小

**官方要求**：「对画面中特定**颜色或形状目标**的动态跟踪，叠加**跟踪标识或坐标信息**」

- 在"基础扩展②"的质心基础上加：帧间位移 → 方向/速度判决（状态机）→ 准星/轨迹线
- 坐标文字已由 ② 提供，这里只加方向判决
- **预算**：约 **150 slice**
- **参考**：`x-hao-v/fpga-video-gesture-control` 的"检测→决策→画面响应"闭环

### 高阶挑战(5) 自动曝光/白平衡 —— 建议**不做**

- 官方 `awb.v` 已有 AE/AG 通路，但**策略是官方的、文件不能改**（`docs/17` L1）
- 自己另做一套要抢 I2C 控制权、跟官方 `uics520_cfg` 打架，**风险高、收益低**
- **替代方案**：把现有 awb 的增益值读出来**上屏显示**（复用 OSD），作为"图像质量调节"的观察证据，成本 ~100 slice。评委问起来能讲，但不宣称实现了自动调节。

## 七、一句话总结

**基础功能 4/4 已完成，但"系统稳定性（光线剧烈变化）"缺实测证据，必须先补测。**
**扩展按官方 2.6 的真实结构是"2 个基础扩展 + 5 个高阶挑战"，不是"5 条"：2 个基础扩展是拿一半分的入场券（我们现在 0/2），5 个高阶挑战才是拉分点（0/5）。**
**打法：先切自研 OSD 腾出 2,319 slice，然后靠"一套窗口生成器 + 后级算子 mux + 复用现成 OSD 字符库"把 7 项塞进去，预算 77.8%。**
